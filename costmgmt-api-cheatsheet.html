Introduction

The Cost Management API allows users to obtain all the data available in the UI, and even more since with the API it’s possible to combine filters or to make several API calls and then combine the results.

The latest version of this cheat sheet, and its accompanying Bruno collection, are always available from https://github.com/project-koku/costmgmt-api-cheatsheet.

Below are common scenarios with example API calls.

Base URL: https://console.redhat.com

Authentication

Using service account tokens (OAuth2 client credentials)

Grab your token using the following curl command:

curl -v \
  -d "client_id=CLIENT_ID" \
  -d "client_secret=CLIENT_SECRET" \
  -d "grant_type=client_credentials" \
  -d "scope=api.console" \
  "https://sso.redhat.com/auth/realms/redhat-external/protocol/openid-connect/token"

Use the token in an API request via curl:

curl --location \
  'https://console.redhat.com/api/cost-management/v1/reports/aws/costs/' \
  --header 'Authorization: Bearer ACCESS_TOKEN'

Optimizations (Resource Optimization for OpenShift)

Notification codes (reference)

Machine-readable catalog of all notification codes (no auth required). Optional filter[plugin] for container, namespace, node, gpu, pvc, snapshot, vm, quota, or cluster-quota.

GET /api/cost-management/v1/recommendations/openshift/notification-codes
GET /api/cost-management/v1/recommendations/openshift/notification-codes?filter[plugin]=container
GET /api/cost-management/v1/recommendations/openshift/notification-codes?filter[plugin]=namespace

Code 77 (SPARSE_DATA, severity INFO) — Recommendation based on limited data; accuracy improves with more observation time — is emitted on container, namespace, node, and PVC recommendations when data_days is at or below sparse_data_threshold (default 2). It does not apply to GPU recommendations.

Fleet summary

Cross-cluster aggregated savings, adoption rates, and top optimization opportunities:

GET /api/cost-management/v1/recommendations/openshift/fleet-summary

Fleet savings summary

Aggregated monthly savings by plugin (container, node, PVC, snapshot, VM). Container, node, and VM totals honor ?engine=cost (default) or performance. GPU dollar estimates are computed at API read time and are excluded from this rollup (by_plugin.gpu is always 0; see gpu_savings_note).

Use ?term=short, ?term=medium (default), or ?term=long to align node/container/PVC rollups with the same term window as list APIs. VM savings use mapped term keys (short_term, medium_term, long_term).

Requires persisted recommendations for the selected term. VM rows need ROS_SAVINGS_ESTIMATES_ENABLED=true and KOKU_MASU_URL at ingestion time for non-zero by_plugin.vm.

GET /api/cost-management/v1/recommendations/openshift/savings-summary
GET /api/cost-management/v1/recommendations/openshift/savings-summary?engine=cost
GET /api/cost-management/v1/recommendations/openshift/savings-summary?engine=cost&term=short
GET /api/cost-management/v1/recommendations/openshift/savings-summary?filter[cluster]=<cluster-uuid>&group_by[tag:environment]=*
GET /api/cost-management/v1/recommendations/openshift/savings-summary?group_by[tag:environment]=*
GET /api/cost-management/v1/recommendations/openshift/savings-summary?group_by[tag:environment]=*&filter[project]=payments
Note
 filter[cluster] is only applied when a group_by parameter is present (e.g., group_by[tag:*] or group_by[idle_state]). filter[project] scopes container savings in tag-grouped responses only (requires group_by[tag:*]). Without group_by, cluster and project filters have no effect and all RBAC-visible clusters are included.

PVC plugin totals in by_plugin honor term only (engine-agnostic). Snapshot totals are term-independent (always sum all snapshot recommendations regardless of term). Container, node, and VM totals honor both engine and term.

Negative savings

When current resource requests are already below the recommended target, estimated_monthly_savings.value (containers, nodes, PVCs, VMs) can be negative. That indicates an additional monthly cost if the recommendation is adopted (upsize for reliability or performance), not a savings opportunity. The UI should label negative values as additional cost rather than "Savings: -$X/month".

Effective rates (Koku Masu)

ROS does not expose a standalone cost-rate API. During ingestion (and savings recalculation), ros-processor fetches rates from Koku Masu:

GET /api/cost-management/v1/effective_rates/?cluster_id=<cluster-id>&org_id=<org-id>&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD

Returns the cluster cost model rates used for savings: CPU/memory request and usage rates per hour, storage rates per month, node_cost_per_month, optional gpu_cost_per_month, markup, distribution_type, and per-namespace aggregates (cost_model_cpu_cost, infrastructure_cost, distributed_cost, etc.). ROS caches the response per cluster for the ingest cycle.

When rates are missing or Masu is unreachable, recommendations still persist but dollar fields are omitted or zero and notification code 25 (NotifNoCostData) is appended on container, node, and PVC rows. Fleet savings-summary exposes by_cluster[].has_cost_data: false when every recommendation in that cluster lacks cost data.

Requires KOKU_MASU_URL on ros-processor/ros-api and ROS_SAVINGS_ESTIMATES_ENABLED=true (default).

Fleet heatmap

CPU and memory utilization heatmap across all clusters, showing hourly resource usage patterns. Requires Visual Insights enabled (ROS_VISUAL_INSIGHTS_ENABLED=true).

GET /api/cost-management/v1/recommendations/openshift/fleet-heatmap
GET /api/cost-management/v1/recommendations/openshift/fleet-heatmap?metric=memory
GET /api/cost-management/v1/recommendations/openshift/fleet-heatmap?filter[cluster]=CLUSTER_UUID

Default metric is cpu. Use ?metric=memory for memory heatmap. Response returns a matrix of hourly utilization data points across nodes.

Savings recalculation (internal)

After a Koku cost model update, masu notifies ROS to refresh persisted dollar savings without re-ingestion. Supported types: container, node, pvc, quota, cluster-quota. Service-account bearer token required (same auth as tag sync). Requires ROS_SAVINGS_ESTIMATES_ENABLED and ROS_SAVINGS_RECALCULATION_ENABLED.

OpenShift Virtualization (VM) monthly savings are not refreshed by this endpoint. VM estimated_monthly_savings on list/detail and by_plugin.vm in GET /savings-summary are computed during VM recommendation ingestion when ROS_SAVINGS_ESTIMATES_ENABLED=true and KOKU_MASU_URL is available; a new ingest cycle is required after cost model rate changes.

Plugin / type recalculate-savings support

container, node, pvc, quota, cluster-quota

Supported — pass in recommendation_types

container (GPU MIG/idle)

Included when container is in recommendation_types — refreshes estimated_gpu_savings_cents

vm

N/A — computed at ingestion (not via recalculate)

snapshot

N/A — snapshot totals are term-independent; uses settings/env rate chain

gpu (time-slicing)

N/A — persisted as estimated_savings_cents at ingest (not via recalculate); run ingest or [Backfill GPU time-slicing] after rate changes

Container recommendations

GET /api/cost-management/v1/recommendations/openshift/

Recommendations for a specific container (use the recommendation UUID):

GET /api/cost-management/v1/recommendations/openshift/{recommendation_uuid}

Legacy aliases (identical behavior): GET /api/cost-management/v1/recommendations/openshift/container, GET …​/openshift/container/{recommendation_uuid}.

The detail response includes per-term (short/medium/long) recommendations for two models:

  • Cost model: optimizes for resource savings (p60 CPU / p95 memory)

  • Performance model: optimizes for headroom (p98 CPU / p100 memory)

Each recommendation includes CPU/memory requests and limits, per-engine notifications on detail, and usage distribution plots under recommendation_terms.<term>.plots.plots_data. Each time bucket maps to cpuUsage and memoryUsage objects with percentile fields (p50, p95, p99, max) and a format (cores for CPU, MiB for memory). Container boxplots also include an optional cpuThrottle object (P95 + Max in cores); omitted when no throttling occurred. Values are assembled from daily digests (not raw samples).

Notifications: Detail responses emit notifications maps only on recommendation_engines.<engine> (not at term or top-level). List rows expose recommendations.notification_codes (deduplicated integer array); resolve badge text via GET …​/notification-codes.

Example plot bucket:

{
  "cpuUsage": { "p50": 0.12, "p95": 0.45, "p99": 0.67, "max": 0.89, "format": "cores" },
  "cpuThrottle": { "p95": 0.03, "max": 0.12, "format": "cores" },
  "memoryUsage": { "p50": 256.0, "p95": 384.0, "p99": 420.0, "max": 512.0, "format": "MiB" }
}
Note
 cpuThrottle is only present for container recommendations (not namespace). It is omitted entirely when both P95 and Max are zero (no throttling in that bucket).

Detail responses nest both engines under each term:

recommendations.recommendation_terms.medium_term.recommendation_engines.cost
recommendations.recommendation_terms.medium_term.recommendation_engines.performance

How engines differ (cost vs performance)

  • Cost — lower usage percentiles (e.g. P60 CPU, P95 memory) to right-size for savings

  • Performance — higher percentiles (e.g. P98 CPU, max memory) to preserve headroom

On list endpoints, filter[engine]=cost or filter[engine]=performance returns only the selected engine under each term and omits the other from recommendation_engines. When the filter is omitted, both engines are returned.

To generate cluster data where cost and performance sizing intentionally diverge (for validation or demos), use the NISE fixture at nise/examples/ocp_dual_engine/ (spike-cpu-api, steady-mem-worker workloads; see the README in that directory).

Testing divergence

After ingesting nise/examples/ocp_dual_engine/ data, container cost vs performance sizing will differ under recommendation_terms.*.recommendation_engines (higher CPU/memory on performance for spike-prone workloads). Use that fixture in your test cluster to verify dual-engine divergence in E2E, IQE, or Bruno manual runs; generic fixtures may return identical sizing while still exposing both engine blocks.

OOM Timeline

Per-day OOM (Out of Memory) kill counts for a container. Returns only days with at least one OOM event (sparse response). Defaults to the last 6 months.

GET /api/cost-management/v1/recommendations/openshift/containers/{recommendation_uuid}/oom-timeline
GET /api/cost-management/v1/recommendations/openshift/containers/{recommendation_uuid}/oom-timeline?start_date=2026-01-01&end_date=2026-06-29

Example curl:

curl -s -H "x-rh-identity: $IDENTITY" \
  'https://console.redhat.com/api/cost-management/v1/recommendations/openshift/containers/RECOMMENDATION_UUID/oom-timeline?start_date=2026-01-01' \
  | python3 -m json.tool

Example response:

{
  "meta": {
    "count": 9,
    "container_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "start_date": "2026-01-01",
    "end_date": "2026-06-29"
  },
  "data": [
    {"date": "2026-03-15", "oom_kill_count": 3},
    {"date": "2026-03-22", "oom_kill_count": 1},
    {"date": "2026-04-01", "oom_kill_count": 5}
  ]
}

meta.count is the sum of all oom_kill_count values (total OOM events, not total days). Empty data array when no OOM events occurred in the range.

Filtering and sorting

Filter by cluster, project, workload, workload type, or container:

GET /api/cost-management/v1/recommendations/openshift/?filter[cluster]=CLUSTER_UUID
GET /api/cost-management/v1/recommendations/openshift/?filter[project]=my-namespace
GET /api/cost-management/v1/recommendations/openshift/?filter[namespace]=my-namespace
GET /api/cost-management/v1/recommendations/openshift/?filter[workload]=my-deployment
GET /api/cost-management/v1/recommendations/openshift/?filter[workload_type]=deployment
GET /api/cost-management/v1/recommendations/openshift/?filter[container]=my-container

filter[namespace] is an alias for filter[project] (both filter by OpenShift namespace). Legacy flat forms (cluster_uuid, project, namespace, container) are also accepted.

filter[workload_type] accepts any lowercase Kubernetes workload kind (exact match; comma-separated values are ORed), e.g. deployment, statefulset, domain. Legacy flat form ?workload_type=deployment is also accepted. Invalid formats return 400; any syntactically valid kind string is accepted.

Filter by recommendation engine (limits nested recommendation_engines to cost or performance; omits the non-selected engine from each item):

GET /api/cost-management/v1/recommendations/openshift/?filter[engine]=cost
GET /api/cost-management/v1/recommendations/openshift/?filter[engine]=performance

Legacy flat ?engine=cost is also accepted on container, namespace, node, VM, quality, and history endpoints.

Filter by recommendation term

Limit results to a specific recommendation term. When omitted, all terms are returned.

GET /api/cost-management/v1/recommendations/openshift/?filter[term]=medium_term

Valid values: short_term, medium_term, long_term

Legacy flat parameter ?term=short is also accepted. The response recommendation_terms object will only contain the selected term.

Filter by GPU:

GET /api/cost-management/v1/recommendations/openshift/?filter[has_gpu]=true
GET /api/cost-management/v1/recommendations/openshift/?filter[gpu_model]=A100
GET /api/cost-management/v1/recommendations/openshift/?filter[gpu_classification]=underutilized

Filter by idle state (active, idle, or zombie; comma-separated values are ORed):

Note
 The API uses idle_state=zombie which the UI displays as "Abandoned". 
GET /api/cost-management/v1/recommendations/openshift/?filter[idle_state]=zombie,idle

Filter by stale data (false = fresh only (default), true = include stale and fresh, only = stale rows only). A recommendation is stale when the cluster has not reported within ROS_STALENESS_THRESHOLD_HOURS (default 48). Legacy ?stale= accepted:

GET /api/cost-management/v1/recommendations/openshift/?filter[stale]=false
GET /api/cost-management/v1/recommendations/openshift/?filter[stale]=only

Exact-match and exclude filters are supported on cluster, project, workload, and container:

GET /api/cost-management/v1/recommendations/openshift/?filter[exact:cluster]=EXACT_UUID
GET /api/cost-management/v1/recommendations/openshift/?exclude[project]=openshift-monitoring

Filter by OpenShift labels (requires ROS_TAGS_ENABLED=true; tags synced from Koku):

GET /api/cost-management/v1/recommendations/openshift/?filter[tag:environment]=production
GET /api/cost-management/v1/recommendations/openshift/?filter[tag:environment]=production,staging
GET /api/cost-management/v1/recommendations/openshift/?filter[tag:team]=platform

Tag filter syntax follows Koku report conventions:

  • filter[tag:<key>]=<value> — exact value match

  • filter[tag:<key>]=a,b — OR within the same key (comma-separated)

  • Multiple filter[tag:*] keys — AND across keys

  • filter[tag:<key>]=* — key present with any value

  • Legacy flat form ?tag=<key>:<value> is also accepted

Note
 filter[tag:key] is supported on list endpoints and fleet history (GET …​/history). It is NOT supported on per-resource detail endpoints (GET …​/containers/{id}, etc.).
Tag sync configuration

  • ROS_TAGS_ENABLED (default: true) — master switch for tag filters and tag group_by on savings summary

  • ROS_TAGS_SOURCE (default: api on cost-onprem chart and SaaS; db optional on-prem) — api uses Koku push sync into ROS resolved_tags; db reads Koku PostgreSQL tag tables at query time (requires shared DB access)

  • Tag keys must be enabled in Cost Management Settings → Tags; discover keys via GET /api/cost-management/v1/tags/openshift/

For the complete machine-readable parameter list, see openapi.json.

When a tag key is unknown or has no matching containers, meta.count is 0 and meta.warnings may describe the empty result.

When filter[tag:key]=value is combined with RBAC-scoped identity, results are the intersection of allowed clusters/namespaces AND tag matches. A tag filter scoped to a cluster outside RBAC scope returns HTTP 200 with an empty list (not 403).

ResourceQuota recommendations

Namespace-level Kubernetes ResourceQuota right-sizing (distinct from namespace CPU/memory usage recommendations). Compares configured quota hard limits and used consumption against aggregated container recommendation totals.

Quota savings (estimated_savings) are per-recommendation only. They are NOT included in the fleet GET /savings-summary rollup (which covers container, node, PVC, snapshot, and VM plugins).

ResourceQuota recommendations are not engine- or term-selectable: the quota engine uses fixed term=medium and engine=cost container aggregates (no filter[term] on this API).

When RBAC is enabled, list results are scoped to clusters the caller may read (openshift.cluster). filter[cluster] for an unknown or unauthorized cluster returns 200 with an empty list.

The first ingestion cycle after enabling quota collects namespace quota snapshots; recommendations that depend on container aggregates may appear from the second cycle onward when container CSV is present in the payload.

Object-count metrics (objectcounts. / aggregated object_count_ in operator CSVs) are ingested internally but are not exposed in API quota_hard / quota_used / utilization fields. High object-count utilization still drives raise / high risk_level and notification code 72 (QUOTA_BLOCKING); object-count capacity is not monetized in estimated_savings.

  • throughput_threshold_bps — sustained aggregate rx+tx P95 above this (bytes/sec; default 62500000 ≈ 500 Mbps)

  • pps_threshold — packets-per-second P95 threshold for alternate network-bound path (default 100000)

  • drop_ratio_bp — max daily drop ratio must exceed this in basis points (default 10 = 0.1%) with high PPS

  • sustained_days — days in the term window meeting throughput or PPS+drop criteria (default 7)

  • enable_network_series — when true, network-bound VMs may receive n1.* instance types (default true)

  • high_iops_threshold — total read+write p95 IOPS above this triggers code 39 (VM_HIGH_IO) (default 3000)

  • random_threshold_bytes — average I/O size < this → random and code 59 (default 16384 = 16 KiB); values between random and sequential thresholds yield mixed

  • min_iops_for_classification — peak IOPS below this → low-io (no pattern codes) (default 100)

  • idle_threshold_bp — SM utilization below this → idle classification (default 500 = 5%)

  • compute_saturation_threshold_bp — SM fraction at or above this → compute-saturated (default 8500 = 85%)

  • gpu_timeslice_dram_penalty_threshold_bp — when DRAM ≥ this, max replicas is halved (default 5000 = 50%)

{
  "timezone": "America/New_York",
  "schedule": {
    "days": ["monday", "tuesday", "wednesday", "thursday", "friday"],
    "start_time": "10:00",
    "end_time": "15:00"
  },
  "off_hours_weight": 0.0,

resolved_from is namespace, cluster, org, or none (no schedule applies). timezone uses an IANA name (for example America/New_York); start_time and end_time are interpreted in that timezone’s local wall clock, not as UTC.

When ROS_SETTINGS_LOCKED_BUSINESS_HOURS=true (default when the global settings lock is on), business-hours PUT and DELETE return 403. GET still returns the schedule with settings_locked: true and enabled: false.

PUT returns 202 Accepted and triggers asynchronous digest reship (reship_ros). Cluster GET responses may include reship_status: complete, pending, or forward_only (degraded — forward data only). Org-level GET does not include reship_status.

Overnight windows are allowed: schedule.end_time may be before schedule.start_time (for example Mon–Fri 22:00–06:00). The window is half-open [start, end) on the local wall clock in the IANA timezone (not elapsed duration; DST may skip or repeat an hour). Samples after midnight belong to the previous calendar day’s shift (Friday’s shift includes Saturday morning until end_time). Equal start and end times return 400. 08:00–17:00 in the example below is a typical office window, not the only legal window. PUT may include a non-fatal wrap warning.

enabled: false keeps the override row but disables business-hours digest generation for that scope. DELETE removes the override so the scope inherits from cluster or org default.

{
  "timezone": "America/New_York",
  "schedule": {

    "start_time": "08:00",
    "end_time": "17:00"
  },
  "off_hours_weight": 0.0,
  "enabled": true
}

days uses lowercase English day names. start_time / end_time are 24-hour HH:MM in the configured IANA timezone. Not currently being used in the cost management backend

sup_markup

Markup set in the cost model, applied against sup_usage

sup_total

Total combined sup_cost: sup_usage + sup_markup

infra_usage

Cost calculations from rates defined in the price list within a cost model when selecting Infrastructure as the Calculation type

infra_raw

Cost coming directly from a cloud bill

infra_markup

Markup set in the cost model, applied against infra_raw and infra_usage

infra_total

Total combined infra_cost: infra_usage + infra_markup + infra_raw

cost_usage

Total cost of usage: sup_usage + infra_usage

cost_raw

Total cost of raw: sup_raw + infra_raw

cost_markup

Total cost of markup: sup_markup + infra_markup

cost_total

Total combined cost: cost_usage + cost_markup + cost_raw

cost_units

Cost currency unit for all cost metrics

capacity

Total hourly capacity of metric (Memory/core hours)

capacity_count

Max cores/Mem for a cluster

capacity_count_units

Unit for count (e.g. Core)

usage

Total hourly usage for a project/node/cluster and/or day/month depending on the query

usage_units

Unit for the usage/request/limit metrics (e.g. Core-hours)

request

Total hourly request for a project/node/cluster and/or day/month depending on the query

request_unused

Total hourly request that is not being utilised (difference between request and usage)

request_unused_percent

Percent value for unused cluster request based on (unused_request / capacity) * 100

limit

Total hourly limit for a project/node/cluster and/or day/month depending on the query

gpu_request

Total GPU device requests for a project/node/cluster

gpu_limit

Total GPU device limits for a project/node/cluster

gpu_usage

Total GPU utilization for a project/node/cluster (in device-hours)
